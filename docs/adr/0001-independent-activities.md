# 活动独立于素材，并通过投放复用于多个地图

店铺打卡与弹幕留言需要在 Web 中独立管理，并将参与者产生的数据与普通素材分开。同一活动可关联多个地图；地点与参与规则属于活动，投放只决定关联地图和启停。因此引入独立的 Activity，区分活动定义、地图关联和参与记录。

2026-10-28 用户进一步确认：店铺有固定地点，不能随投放地图变化。这取代首版“每次投放维护坐标与规则覆盖”的设计。活动内容中修改地点后，所有关联地图读取同一份地点；参与记录仍按投放区分来源。

活动领域实现位于 `lib/activities/`，Web 和小程序采用独立活动接口。接口和权限行为以[后端契约](../team-workbench-backend-contract.md)与[小程序 API](../miniapp-api.md)为准。

## 现状与原因

- [`AssetFileType`](../../lib/content-model/contracts.ts) 将 `shop` 纳入素材类型；[`ShopPlaceForm`](../../app/manage/components/placements/ShopPlaceForm.tsx) 在地图上下文中同时创建店铺素材与投放。
- [`submitAnonymousText`](../../lib/placements/runtime.server.ts) 将每条小程序留言写为普通文字 Asset 和 Placement，缺少独立的活动归属。
- 相邻小程序仓库的 `miniprogram/components/shop-checkin/index.js` 仅在手机本地保存打卡结果，Web 尚无对应的服务端参与记录。

仅移动表单入口或给 Asset 增加活动分类，仍会把活动规则、素材和参与数据混在同一模型中。独立活动需要新增管理与数据处理流程，但能让活动的创建、复用、投放和参与记录各自具有明确身份。

## 决策

1. 活动独立于 Asset 和 Scene，由团队管理；创建活动不要求先选择地图。
2. 店铺打卡、弹幕留言属于活动类型。活动使用的图片、奖励图等内容可以引用普通素材；参与者产生的留言和打卡记录属于活动数据。
3. 一场店铺打卡活动包含多个打卡点，每个点具有可区分的身份。打卡点属于活动内容，活动投放关联整场活动与地图；单个点不等同于一场活动或一次活动投放。
4. 活动与地图通过活动投放关联。同一活动可以投放到多个地图，每次关联有独立身份和启停状态，不复制地点或规则。打卡点的固定地点、弹幕活动的参与区域均在活动内容中管理。
5. 活动记录保留所属活动与具体投放，支持按投放查看及按活动汇总；共享活动定义不能丢失数据来源。打卡记录还必须标识具体打卡点，不能仅记录参与过哪场活动。
6. Web 提供独立活动管理入口，在店铺打卡活动内管理多个打卡点。地图编辑器选择活动并管理投放，小程序根据投放提供对应互动。

## 后续实现的约束

- 沿用团队权限模型，分别校验活动、地图和记录的团队归属。匿名参与接口不授予活动管理权限。
- 地点和规则只有活动定义这一处来源；投放不提供位置、规则覆盖或单点启停。迁移已有多份坐标时，冲突须显式处理，不能静默选一份覆盖。
- 活动记录与普通素材在持久化、管理查询和写入路径上分开。复用渲染代码不要求将留言重新存成 Asset。
- 新增活动记录需要服务端写入路径；现有手机本地打卡记录无法通过数据库迁移自动还原。
- 迁移店铺时明确旧素材、旧投放与新活动、打卡点和活动投放的身份对应，保护已有入口和客户端记录依赖的标识。历史店铺需按明确的分组依据组织为活动下的打卡点，不能默认一条旧 shop 就是一场活动。
- 历史弹幕优先依据 `origin = public_submission` 和已有审计证据识别来源；不能将所有文字素材批量视为弹幕，来源不明的数据需保留并核对。
- 改动当前小程序接口时同步处理消费者与发布顺序。本文不提前定义新的接口路径、数据库表结构或替换现有公开协议。

## 首版执行规则

- 参与记录和公开留言按活动投放隔离，管理页按活动汇总；不同地图的打卡进度不互通。
- 小程序使用设备随机参与标识，同一设备在同一投放对同一点只记一次打卡。记录可由团队管理人员隐藏和恢复，归档不删除历史。
- 按用户明确确认，2026-10-28 生产备份中的 899 条历史文字全部保留为普通地图 Asset，原投放不变；新弹幕写入活动记录。
- 全面切换到新架构，移除旧 shop Asset 类型、旧店铺/文字提交接口和组织级店铺功能开关，不保留运行时兼容分支。迁移保留原始快照及映射供核对、恢复，数据库与双端应用需配套发布。
