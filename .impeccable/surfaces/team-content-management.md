# Team content management

- Scope: delivered team-content management UI and its integration from the team-assets/scenes refactor plan (§6): asset library (`/manage/assets`), asset detail (`/manage/assets/[id]`), scene list (`/manage/scenes`), independent scene save/publish controls, Placement management on `/manage`, project roles and membership on `/admin/workspaces`, and fixed-content upload-and-place on `/upload-onsite`. Mode: Operate. The scene editor (`/manage/scenes/[id]`) keeps its own brief as the authority for its Unity/Timeline layout; current content-model behavior comes from `PRODUCT.md`, the refactor plan and this brief.
- Audience and job: organization members who find, reuse and maintain shared assets across projects, compose and publish a project's scenes, and manage individual placements; project managers who assign permitted project roles; onsite contributors who confirm a location and upload content. The main task is finding and reusing a pinned version, then acting on the intended project or placement.
- Extension of the incumbent management console: semantic tokens, `components/ui` primitives, `<Text>` three-zone typography, Geist plus Chinese system fonts. No new palette, fonts, hero metrics or icon-card grids. Approved as a settled extension; no concept round.
- Structure: asset and scene lists use dense hairline-divided rows inside one bordered region; columns on desktop, stacked metadata on narrow screens. Details use bordered sections; map, editor and onsite workflows retain their incumbent task layouts. One primary action per task state (upload, upload new version, create scene, save or publish). Destructive colour is reserved for irreversible actions; archive and revoke are reversible and use neutral controls with an explicit effect statement.
- Product truths the UI must state: references are pinned to versions; a new AssetVersion never changes existing drafts, publications or placements. Scene saves update a project-owned draft; publication creates an immutable SceneRevision, with placement updates explicitly selected. A Placement references one AssetVersion or SceneRevision and owns its position, display settings and status. Archive keeps existing references working and blocks new use; revoking a project grant with dependencies is refused with an impact list; restricted dependencies show counts, not names. Lifecycle and usage remain separate: the active asset filter is labelled “未归档” in Chinese, while usage reports “未使用” or a reference count.
- States: loading skeleton rows, scoped empty states that teach the next step, filtered-empty with clear filters, error with retry, stale-lock conflict with reload or local draft recovery, permission-limited read-only notes, and organization migration-state notices. Role controls follow server capabilities; onsite capture requires explicit location confirmation before each placement.
- Component boundary: `app/manage/content` remains a presentational layer. Data and decisions enter through props and async callbacks returning `ContentActionResult`; no fetches, stores or endpoint DTOs in that layer. Route components, hooks and adapters outside it own context, API calls, DTO mapping, permissions and persistence. Presentation states live in `stories/content`; integration states live in `stories/manage/content-integration`.
- Product boundary: no activity, topic, tree or collection UI. Tree activities remain content-resolution, business-command and display-adapter extension seams only.
